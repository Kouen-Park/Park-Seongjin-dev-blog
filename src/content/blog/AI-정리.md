요즘 코딩 AI를 이것저것 사용하다 보니 문제가 하나 생겼습니다.

**너무 많습니다.**

Cursor, Claude Code, Codex, OpenCode, Goose, Cline, Kilo Code, Devin, OpenHands...

거기에 모델까지 내려가면 GPT, Claude, Gemini, DeepSeek, Qwen, Llama, Kimi...

처음에는 그냥

> "코딩 잘해주는 AI 아닌가?"

라고 생각했는데 보다 보니 전혀 아니었습니다.

어떤 것은 **AI 모델**이고,

어떤 것은 그 모델을 사용하는 **코딩 도구**이고,

어떤 것은 아예 컴퓨터 하나를 넘겨주고 일을 시키는 **자율형 에이전트**에 가깝습니다.

특히 이런 질문들이 계속 생겼습니다.

> "Cursor랑 OpenCode는 뭐가 다른 거지?"

> "DeepSeek이나 Llama를 쓴다는 건 정확히 무슨 뜻이지?"

> "오픈소스랑 오픈웨이트는 같은 건가?"

> "Devin은 Cursor보다 그냥 더 똑똑한 건가?"

그래서 한번 정리해보기로 했습니다.

미래의 제가 새로운 AI 툴이 나올 때마다 처음부터 다시 공부하지 않기 위해서입니다.

## 일단 '두뇌'와 '도구'를 분리해야 한다

가장 먼저 헷갈렸던 부분입니다.

**AI 모델과 AI 코딩 도구는 같은 것이 아닙니다.**

아주 단순하게 생각하면,

```text
AI 모델 = 두뇌
AI 코딩 도구 = 두뇌에게 일을 시키는 작업 환경
```

입니다.

예를 들어 Claude는 모델이고,

Cursor는 Claude 같은 모델을 이용해서 코드를 읽고 수정할 수 있게 해주는 도구입니다.

OpenCode 역시 자체적으로 거대한 언어 모델을 훈련하는 프로젝트가 아니라 여러 모델을 연결해서 코딩 작업을 수행할 수 있게 해주는 **코딩 에이전트**입니다.

이걸 구분하고 나니 갑자기 생태계가 조금 덜 복잡해졌습니다.

조금입니다.

## 모델부터: 클로즈드 웨이트 vs 오픈 웨이트

먼저 두뇌부터 나눠보겠습니다.

크게 보면 AI 모델은 **클로즈드 웨이트(Closed-weight)**와 **오픈 웨이트(Open-weight)**로 구분할 수 있습니다.

```text
               AI 모델
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
   Closed-weight        Open-weight
        🔒                  🔓
```

### 클로즈드 웨이트

대표적인 상용 모델 계열로는 OpenAI의 GPT, Anthropic의 Claude, Google의 Gemini 등이 있습니다.

여기서 중요한 것은 **서비스 이름이나 회사 전체가 아니라 개별 모델**입니다.

예를 들어 Google에는 Gemini와 별도로 공개 가중치 모델인 Gemma도 있기 때문에,

> Google = 전부 클로즈드

라고 생각하면 또 틀립니다.

클로즈드 웨이트 모델은 핵심 가중치를 직접 내려받아 실행하는 방식이 아니라 제공 업체의 서비스나 API를 통해 사용하는 것이 일반적입니다.

장점은 단순합니다.

**대체로 강력합니다.**

대규모 인프라와 연구비를 투입해 학습하고, 도구 사용이나 추론 기능까지 제품과 함께 최적화되어 있는 경우가 많습니다.

대신 비용과 통제권 문제가 있습니다.

API를 사용하면 사용량에 따라 비용이 발생할 수 있고, 제공 업체의 정책이나 모델 변경에도 영향을 받습니다.

회사 코드를 외부 API로 보내야 하는 환경이라면 데이터 처리 정책 역시 확인해야 합니다.

### 오픈 웨이트

반대쪽에는 Llama, Qwen, DeepSeek 계열 등 공개 가중치를 제공하는 모델들이 있습니다.

여기서 하나 조심할 것이 있습니다.

**오픈 웨이트 = 오픈소스는 아닙니다.**

가중치를 다운로드할 수 있다고 해서 학습 데이터, 학습 코드, 라이선스까지 전부 자유롭게 공개되어 있다는 뜻은 아닙니다.

모델마다 라이선스와 공개 범위가 다릅니다.

그래서 정확히는

> **모델의 학습된 가중치를 다운로드해서 직접 실행할 수 있다**

정도로 이해하는 것이 좋습니다.

이게 상당히 큰 차이를 만듭니다.

충분한 하드웨어가 있다면 모델을 직접 내려받아서 인터넷 없이 실행할 수도 있습니다.

코드가 외부 모델 제공자의 서버로 가지 않는 구성을 만들 수도 있습니다.

물론 여기에는 중요한 조건이 하나 붙습니다.

**충분한 하드웨어가 있다면.**

제 MacBook Air M2 8GB에 거대한 최신 코딩 모델을 내려받는다고 갑자기 데이터센터가 되지는 않습니다.

세상은 그렇게 친절하지 않았습니다.

## 오픈소스와 오픈웨이트도 다르다

여기서 또 하나 헷갈리는 개념이 있습니다.

**오픈소스 코딩 도구**와 **오픈웨이트 AI 모델**입니다.

예를 들어 OpenCode나 Goose는 오픈소스 **도구**입니다.

반면 Llama나 Qwen 같은 것은 오픈웨이트 **모델**입니다.

즉,

```text
Qwen / Llama / DeepSeek
        ↓
       두뇌

OpenCode / Goose
        ↓
    두뇌를 사용하는 도구
```

라고 볼 수 있습니다.

그래서 OpenCode를 설치했다고 해서 AI 모델이 같이 생기는 것은 아닙니다.

모델 제공자를 연결해야 합니다.

반대로 Qwen 모델 파일을 다운로드했다고 해서 갑자기 프로젝트 폴더를 알아서 돌아다니며 코드를 수정하는 것도 아닙니다.

**두뇌만 책상 위에 올려놓은 상태**에 가깝습니다.

그 두뇌에게 파일을 읽게 하고, 터미널을 실행하게 하고, 코드를 수정하게 만드는 것이 OpenCode나 Goose 같은 도구의 역할입니다.

## 그럼 Cursor, OpenCode, Devin은 뭐가 다른가

여기서부터는 모델이 아니라 **도구의 형태**를 봐야 합니다.

처음에는 코딩 AI를 세 단계 정도로 나누면 이해하기 쉬웠습니다.

```text
AI 에디터
   ↓
코딩 에이전트
   ↓
자율형 개발 에이전트
```

다만 이건 공식적인 산업 표준 분류는 아닙니다.

요즘 도구들이 서로의 기능을 빠르게 흡수하고 있어서 경계도 계속 흐려지고 있습니다.

그래도 개념을 잡기에는 꽤 편합니다.

### 1. AI 코드 에디터

대표적인 예는 **Cursor**와 **Zed**입니다.

기본적으로 중심에는 여전히 **내가 사용하는 코드 에디터**가 있습니다.

제가 코드를 작성하고,

AI가 자동완성을 해주거나,

코드에 대해 질문하거나,

필요하면 여러 파일을 수정하도록 시킵니다.

요즘 Cursor 같은 제품은 에이전트 기능까지 강해져서 단순한 "자동완성 에디터"라고 부르기에는 이미 훨씬 많은 일을 합니다.

그래도 사용 경험의 중심이 **에디터**라는 점은 여전히 구분하기 좋습니다.

쉽게 말하면,

> **내가 운전하고 AI가 옆에서 도와주는 형태**

에 가깝습니다.

### 2. 코딩 에이전트

OpenCode, Goose, Aider 같은 도구는 시작점이 조금 다릅니다.

제가 직접 모든 파일을 열고 수정하기보다는 목표를 줍니다.

> "로그인 기능 추가해줘."

> "이 테스트가 왜 실패하는지 찾아서 고쳐줘."

그러면 에이전트가 프로젝트 파일을 읽고,

필요한 파일을 수정하고,

명령어를 실행하고,

테스트 결과를 보고 다시 코드를 수정합니다.

즉,

```text
사람
 ↓
목표 전달
 ↓
Agent
 ├─ 파일 탐색
 ├─ 코드 수정
 ├─ 명령 실행
 ├─ 테스트
 └─ 다시 수정
```

같은 루프가 만들어집니다.

비유하자면 Cursor가 옆자리의 페어 프로그래머라면,

이쪽은

> "이거 해놓고 결과 알려줘."

라고 일을 넘기는 느낌에 조금 더 가깝습니다.

물론 아직 결과 확인은 해야 합니다.

AI에게 `rm` 권한까지 줘놓고 믿음으로 개발하는 단계까지 갈 필요는 없습니다.

### 3. 더 독립적으로 일하는 개발 에이전트

Devin이나 OpenHands 같은 제품은 이 개념을 한 단계 더 확장합니다.

코드 파일만 수정하는 것이 아니라 **독립적인 실행 환경** 안에서 작업하도록 설계됩니다.

작업에 따라

```text
환경 확인
   ↓
코드 작성
   ↓
명령 실행
   ↓
테스트
   ↓
브라우저 확인
   ↓
디버깅
   ↓
Git 작업
```

같은 긴 작업 흐름을 맡길 수 있습니다.

그래서 흔히 "AI Software Engineer" 같은 표현이 등장합니다.

다만 여기에도 주의할 점이 있습니다.

**코딩 에이전트와 AI 엔지니어 사이에 마법의 경계선이 있는 것은 아닙니다.**

OpenCode 같은 도구도 shell과 여러 도구를 사용해 상당히 자율적으로 움직일 수 있고, 다른 에이전트들도 브라우저나 샌드박스를 붙이면서 기능 범위가 계속 넓어지고 있습니다.

결국 중요한 것은 이름보다

> **AI에게 어느 정도의 환경과 권한을 주고, 얼마나 긴 작업을 스스로 수행하게 하느냐**

입니다.

## 로컬 모델의 현실적인 문제

여기까지 알아보고 나면 이런 생각이 듭니다.

> "그러면 OpenCode에 Qwen이나 DeepSeek 연결해서 로컬로 돌리면 무료 아닌가?"

이론적으로는 맞습니다.

문제는 제 노트북입니다.

대형 모델을 제대로 실행하려면 상당한 메모리와 연산 성능이 필요합니다.

특히 코딩 에이전트는 한 번 질문하고 끝나는 것이 아니라

```text
생각
→ 파일 읽기
→ 생각
→ 수정
→ 테스트
→ 에러 읽기
→ 다시 생각
```

을 반복합니다.

작은 모델을 억지로 로컬에서 돌리다가 기다리는 시간이 길어지면,

무료로 아낀 API 비용을 **제 수명으로 지불하는 기분**이 들 수도 있습니다.

그래서 흥미로운 중간 지점이 생겼습니다.

## 오픈소스 도구 + 저렴한 클라우드 모델

대표적인 예가 **OpenCode Go**입니다.

OpenCode 자체는 오픈소스지만, 모델 추론은 클라우드에서 제공받는 방식입니다.

현재 OpenCode Go는 첫 달 $5, 이후 월 $10이고, 여러 코딩 모델을 사용할 수 있습니다.

중요한 점은 **무제한은 아니라는 것**입니다.

OpenCode 측 설명으로는 월 $10에 대해 대략 그보다 6배 수준의 사용 가치를 제공하는 것을 목표로 하고 있으며, 모델마다 실제 사용량은 달라질 수 있습니다.

즉,

```text
내 컴퓨터
    ↓
OpenCode
    ↓
클라우드 모델
```

구조입니다.

이 방식이 개인적으로 꽤 흥미롭습니다.

비싼 GPU는 필요 없고,

OpenCode라는 오픈소스 도구는 그대로 사용할 수 있고,

모델만 클라우드에서 빌려옵니다.

**소프트웨어는 내 마음대로 고르고, GPU는 남의 것을 빌리는 셈입니다.**

## CLI가 싫다면 데스크톱도 있다

코딩 에이전트라고 하면 검은 터미널부터 떠올리기 쉽습니다.

저도 CLI를 쓰기는 하지만 가끔은 그냥 창 하나 띄워놓고 쓰고 싶습니다.

다행히 선택지가 꽤 있습니다.

### OpenCode

OpenCode는 오픈소스 AI 코딩 에이전트이고 현재 터미널 인터페이스뿐 아니라 **데스크톱 앱과 IDE 확장**도 제공합니다.

또 특정 모델 하나에 묶이지 않고 여러 모델 제공자를 연결할 수 있다는 것이 큰 특징입니다.

2026년 9월 기준 프로젝트 자체에 표시된 GitHub Star 수는 약 **20.8만 개** 수준입니다.

다만 한 가지는 기억해야 합니다.

OpenCode의 에이전트는 로컬 머신에서 shell과 파일 시스템 등에 접근할 수 있고, 공식 보안 문서에서도 에이전트 자체가 샌드박스되는 구조는 아니라고 설명합니다.

편리한 만큼 권한도 큽니다.

AI에게 열쇠를 줬다면 최소한 어느 방 열쇠인지는 확인하는 편이 좋겠습니다.

### Zed

Zed는 조금 다른 포지션입니다.

코딩 에이전트 자체라기보다는 **고성능 네이티브 코드 에디터**가 중심입니다.

Rust로 만들어졌고 Atom과 Tree-sitter를 만든 개발자들이 참여한 프로젝트입니다. 현재 GitHub에서는 약 9만 개의 Star를 기록하고 있습니다.

Cursor처럼 AI 기능을 사용하면서도 빠르고 가벼운 네이티브 에디터를 원하는 경우 흥미로운 선택지입니다.

### Goose

Goose는 Block이 시작한 오픈소스 로컬 에이전트 프로젝트입니다.

특정 모델에 강하게 묶이는 대신 다양한 모델을 연결하고, 로컬에서 명령 실행과 파일 수정 같은 작업을 수행하는 방향입니다. 로컬 모델을 연결하면 모델 요청까지 자신의 머신 안에서 처리하는 구성도 가능합니다.

OpenCode와 비슷한 영역에 있지만 철학과 확장 방식이 조금 다르기 때문에 둘을 비교해보는 것도 재미있습니다.

### OpenHands

OpenHands는 좀 더 독립적인 **소프트웨어 개발 에이전트 플랫폼**에 가깝습니다.

에이전트에게 작업 환경을 제공하고 코드 작성부터 명령 실행까지 긴 작업을 맡기는 방향입니다.

2026년 9월 현재 공식 GitHub 저장소는 약 **8.9만 개의 Star**를 기록하고 있습니다.

처음에는 `OpenDevin`이라는 이름으로 시작해서 Devin의 오픈소스 대안으로 많이 알려졌지만, 지금은 자체적인 에이전트 플랫폼으로 보는 편이 더 정확합니다.

## 그래서 뭘 써야 할까

여기까지 정리하고 나니 결국 하나의 도구가 전부를 대체하는 구조는 아니었습니다.

**직접 코드를 많이 작성하면서 AI의 도움을 받고 싶다면**

Cursor나 Zed 같은 AI 에디터가 자연스럽습니다.

**기능 단위로 일을 맡기고 싶다면**

OpenCode나 Goose 같은 코딩 에이전트가 재미있습니다.

**좀 더 긴 작업을 독립된 환경에서 맡기고 싶다면**

Devin이나 OpenHands 같은 형태가 있습니다.

그리고 **인터넷 없이 로컬에서 모델까지 돌리고 싶다면**

Ollama, LM Studio 같은 로컬 런타임에 자신의 하드웨어에서 감당할 수 있는 오픈웨이트 모델을 연결하는 방법이 있습니다.

결국 제가 처음 헷갈렸던 이유는 이 모든 것을 그냥 **"코딩 AI"**라고 한 덩어리로 보고 있었기 때문이었습니다.

실제로는

```text
어떤 두뇌를 쓸 것인가?
        ↓
Closed / Open-weight

그 두뇌를 어디서 돌릴 것인가?
        ↓
Local / Cloud

어떤 도구로 사용할 것인가?
        ↓
Editor / Agent / Autonomous Environment
```

라는 서로 다른 선택이 겹쳐 있었습니다.

이렇게 나누고 나니 새로운 AI 도구가 나와도 조금 보기 쉬워졌습니다.

> "그래서 너는 모델이야, 아니면 그릇이야?"

> "로컬에서 도는 건 앱만이야, 모델까지야?"

> "코드 추천만 해주는 거야, 아니면 터미널까지 건드리는 거야?"

이 세 가지만 물어봐도 대충 정체가 드러납니다.

물론 이 글을 올리고 며칠 뒤 또 새로운 도구가 나올 가능성이 높습니다.

**요즘 AI 생태계에서 가장 빨리 구형이 되는 것은 AI가 아니라 AI 정리글일지도 모르겠습니다.**
